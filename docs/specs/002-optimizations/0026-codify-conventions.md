# 0026 — Codify lessons learned into project governance

**Group:** E — Governance / preventing regressions

## Problem

The optimizations in this spec exist because recurring mistakes shipped without a
guardrail to catch them:

- Backend/auth work (`pingBackend` → `google-auth-library` token mint) was placed
  in prerendered server code (`loading.tsx`, page bodies), which crashes the
  build under Cache Components (synchronous non-deterministic IO: `Math.random`,
  `Date.now`).
- A codemod blanket-applied `export const instant = false` to pages that never
  needed it, masking the real build health of each route.
- Multiple pages render their own `<main>`, nested inside the layout's `<main>`,
  producing invalid HTML and clashing container styles.
- Deprecated config (`images.domains`) lingered until it warned at build time.

These are not one-off bugs; they will recur unless the rules live where agents and
contributors actually read them. Capture the debt as durable conventions so
future work (human or agent) follows them by default.

## Goal

Record the lessons from spec 002 in the project's governance surfaces so they are
enforced going forward:

1. **`AGENTS.md`** (the project constitution; `CLAUDE.md` already `@AGENTS.md`).
2. **OpenSpec living specs** (`openspec/specs/`) where a rule is better expressed
   as a durable capability/requirement than a prose convention.

Choose the right home per rule: cross-cutting "always do this" rules → `AGENTS.md`;
capability-shaped requirements that OpenSpec should track → `openspec/specs/`.

## Conventions to add

Add a new section to `AGENTS.md` (e.g. **"Rendering & Cache Components rules"**)
covering:

1. **No synchronous non-deterministic IO in prerendered server code.** Never call
   `Math.random()`, `Date.now()`, `new Date()`, or `crypto.randomUUID()` in a
   server component / layout / `loading.tsx` / `generateMetadata` that is
   prerendered. If needed, put it behind `<Suspense>` with `await connection()`
   first, wrap it in `"use cache"`, or move it to a Client Component.
2. **No backend / auth / network calls during prerender.** Server-side data
   access (including `pingBackend`, token minting, `fetch`) must be below a
   `<Suspense>` boundary (request-time) or in a `"use cache"` function. Never put
   it at the top of a page/layout or in `loading.tsx`. Reference the
   `BackendWarmup` pattern at `src/components/warmup/BackendWarmup.tsx`.
3. **`loading.tsx` renders an instant, data-free skeleton only.** It is the
   prerendered Suspense fallback — no awaits, no data.
4. **Do not blanket-apply `export const instant = false`.** It only defers
   instant-navigation validation; it does not force dynamic rendering or clear
   prerender errors. Use it only on a specific segment that genuinely must block,
   with an inline comment stating why. Remove codemod-added opt-outs once the
   route passes validation.
5. **Exactly one `<main>` landmark per page — it lives in the root layout.**
   Pages must not render `<main>`; use `<div>` / `<section>` / `<Box>`. The
   layout's `<main>` is the single owner of page width, horizontal centering, and
   base padding — pages must not re-declare `max-w-*` / `mx-auto` / container
   padding that clashes with it. (Reinforces the existing "MUI vs Tailwind"
   styling rules.)
6. **Keep config current.** Use `images.remotePatterns` (not the deprecated
   `images.domains`); treat build-time deprecation warnings as actionable, not
   noise.
7. **`generateStaticParams` must return at least one param** under Cache
   Components (an empty array errors); `dynamicParams` and `runtime = 'edge'` are
   not supported.

Add a lightweight **pre-merge check** note: `npm run build` must pass with zero
prerender errors and zero deprecation warnings before a PR is opened. (Fits the
existing "Pull Request Standard" section.)

## Steps

1. Read `AGENTS.md` and insert the new rules in a coherent section, matching the
   existing tone/format. Keep it concise — link to
   `docs/specs/002-optimizations/` and the Cache Components migration guide rather
   than duplicating long explanations.
2. If any rule is better tracked as an OpenSpec capability, add/update a spec
   under `openspec/specs/` accordingly (consistent with `schema: spec-driven` in
   `openspec/config.yaml`).
3. Do not edit the `<!-- BEGIN:nextjs-agent-rules -->` managed block at the top of
   `AGENTS.md` (it is regenerated by `next dev`).

## Acceptance Criteria

- `AGENTS.md` contains the rendering/Cache Components rules, the single-`<main>`
  rule, and the config-currency rule, in the project's existing style.
- Any OpenSpec living specs added/updated are internally consistent and valid.
- The managed Next.js rules block in `AGENTS.md` is untouched.
- A future agent reading `AGENTS.md` alone would avoid every mistake that spec
  002 had to fix.
